# 👥 Работа в одной ветке (main-new)

Инструкция для работы обоих разработчиков в одной ветке main-new с синхронизацией через GitHub.

---

## 🎯 Преимущества работы в одной ветке

- ✅ Видите изменения друг друга сразу на GitHub
- ✅ Не нужно делать merge между ветками
- ✅ Проще workflow - работаете в main-new
- ✅ Все изменения в одном месте

---

## ⚠️ Важно: Требуются права на запись

Второй разработчик должен быть добавлен как **Collaborator** в репозиторий GitHub.

### Как добавить второго разработчика (для владельца репозитория):

1. Перейдите на GitHub: `https://github.com/GeFoRcE123123/analog`
2. Нажмите **Settings** (вкладка вверху)
3. Выберите **Collaborators** в левом меню
4. Нажмите **Add people**
5. Введите GitHub username или email второго разработчика
6. Выберите роль: **Write** (права на запись)
7. Подтвердите добавление

Второй разработчик получит email-уведомление и должен принять приглашение.

## 🔄 Workflow для работы в одной ветке

### Для обоих разработчиков

#### Утром (перед началом работы)

```bash
# 1. Переключитесь на main-new
git checkout main-new

# 2. Получите последние изменения с GitHub
git pull origin main-new

# 3. Проверьте статус
git status
```

#### Во время работы

```bash
# 1. Делайте изменения в коде...

# 2. Проверьте, нет ли новых изменений (перед коммитом)
git fetch origin
git status

# 3. Если есть новые изменения - получите их
git pull origin main-new

# 4. Добавьте ваши изменения
git add .

# 5. Сделайте коммит
git commit -m "Описание ваших изменений"

# 6. Отправьте на GitHub
git push origin main-new
```

#### Перед каждым push

```bash
# ВСЕГДА проверяйте перед push:
git fetch origin
git pull origin main-new  # Получите изменения другого разработчика
# Разрешите конфликты, если есть
git push origin main-new  # Отправьте ваши изменения
```

## ⚠️ Правила работы в одной ветке

### ✅ Обязательно делать:

1. **Всегда pull перед push** - получайте изменения перед отправкой
2. **Частые синхронизации** - делайте pull несколько раз в день
3. **Понятные сообщения коммитов** - чтобы понимать, кто что изменил
4. **Тестируйте перед push** - не ломайте код другого разработчика
5. **Общайтесь** - сообщайте, когда заливаете большие изменения

### ❌ Не делать:

1. **Не делать force push** - никогда не делайте `git push --force` в main-new
2. **Не игнорировать конфликты** - решайте их сразу
3. **Не коммитьть неработающий код** - код должен компилироваться
4. **Не работать одновременно над одним файлом** - координируйте работу

## 🔀 Решение конфликтов

### Когда возникает конфликт?

Когда оба разработчика изменили один и тот же файл, и один из них сделал push раньше.

### Как разрешить конфликт:

#### Шаг 1: Получите изменения

```bash
git pull origin main-new
```

Git покажет:
```
Auto-merging services/backend/app.py
CONFLICT (content): Merge conflict in services/backend/app.py
```

#### Шаг 2: Откройте файл с конфликтом

Вы увидите маркеры:

```python
<<<<<<< HEAD
# Ваш код
def your_function():
    return "your code"
=======
# Код другого разработчика
def their_function():
    return "their code"
>>>>>>> origin/main-new
```

#### Шаг 3: Разрешите конфликт

**Вариант 1: Объединить оба варианта**
```python
def your_function():
    return "your code"

def their_function():
    return "their code"
```

**Вариант 2: Выбрать один вариант**
```python
# Оставить только нужный код
def combined_function():
    return "combined code"
```

#### Шаг 4: Завершите разрешение

```bash
# 1. Удалите маркеры конфликта из файла
# 2. Добавьте файл
git add services/backend/app.py

# 3. Завершите merge
git commit -m "Разрешен конфликт в app.py"

# 4. Отправьте на GitHub
git push origin main-new
```

## 💡 Стратегии избежания конфликтов

### 1. Работайте над разными файлами

**Хорошо:**
- Разработчик 1: работает над `services/backend/app.py`
- Разработчик 2: работает над `services/parsers/redhat.py`

**Плохо:**
- Оба работают над `services/backend/app.py` одновременно

### 2. Общайтесь перед большими изменениями

```bash
# Сообщите другому разработчику:
"Начинаю работу над app.py, буду изменять функции X и Y"
```

### 3. Делайте частые pull

```bash
# Каждые 30-60 минут
git pull origin main-new
```

### 4. Работайте небольшими коммитами

```bash
# Хорошо: маленькие, логичные коммиты
git commit -m "Добавлена функция parse_cve"
git commit -m "Исправлена ошибка валидации"

# Плохо: один большой коммит в конце дня
git commit -m "Много изменений"
```

## 🔍 Проверка изменений на GitHub

### Как увидеть изменения другого разработчика:

1. **Откройте GitHub:** `https://github.com/GeFoRcE123123/analog`
2. **Перейдите на вкладку Commits** - увидите все коммиты
3. **Или используйте команду:**
```bash
git log --oneline --all --graph
```

### Как увидеть, кто что изменил:

```bash
# История коммитов с авторами
git log --pretty=format:"%h - %an, %ar : %s" -10

# Изменения конкретного файла
git log --oneline services/backend/app.py
```

## 🆘 Решение проблем

### Проблема: "Updates were rejected"

**Причина:** Другой разработчик залил изменения раньше вас.

**Решение:**
```bash
git pull origin main-new
# Разрешите конфликты, если есть
git push origin main-new
```

### Проблема: "Permission denied"

**Причина:** Нет прав на запись в репозиторий.

**Решение:**
1. Попросите владельца добавить вас как Collaborator
2. Примите приглашение на GitHub
3. Попробуйте снова

### Проблема: Много конфликтов

**Решение:**
1. Обсудите с другим разработчиком, кто над чем работает
2. Разделите файлы между собой
3. Делайте pull чаще
